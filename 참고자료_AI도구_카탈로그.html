검증 표기 — 무엇을 어디까지 확인했는가

공개 자료를 그대로 옮겨 적으면 이미 없어진 주소가 섞여 들어옵니다. 그래서 이 카탈로그의 모든 항목은 2026년 8월 5일에 실제로 호출해 응답을 받아 보고 아래 세 등급으로 표기했습니다.

✅ 실호출 확인엔드포인트를 실제로 호출해 응답을 받음. 키가 필요한 API는 "인증키가 없습니다"류 오류 응답을 받은 것을 생존 근거로 삼음(주소가 죽었으면 이 응답조차 오지 않음)
◐ 문서·발급처 확인공식 안내 페이지와 키 발급 창구가 살아 있음을 확인. 호출 규격은 문서 기준
⚠ 확인 실패·유의접속 불가, 요율 제한, 또는 널리 알려진 정보와 실제가 다른 항목. 추정으로 채우지 않고 그대로 표기
⚠ 이 자료 자체에 적용되는 원칙 검증일 기준입니다. 공공 API는 주소·서비스명·응답 규격이 예고 없이 바뀝니다. 실제 분석에 쓰기 전 한 번 호출해 확인하십시오 — 그 확인 작업 자체를 AI에게 시킬 수 있습니다("이 주소 살아 있는지 확인해줘"). 이 문서가 최신이라고 가정하고 수치를 인용하지 마십시오.

10키 발급 · 설치 실무

오늘 하나만 붙여 본다면 이 순서대로

1단계 — 키가 필요 없는 것부터 (5분)

가장 먼저 성공 경험을 만드십시오. 아래 두 개는 발급 절차 없이 즉시 됩니다 (미니실습 ①과 동일).

# ① 법제처 — 소부장 관련 법령 검색 (2026-08-05 실데이터 확인)
curl -s "https://www.law.go.kr/DRF/lawSearch.do?OC=test&target=law&type=XML&query=소재부품장비"

# ② OpenAlex — 전고체 전지 논문 검색 (키 자체가 없음)
curl -s "https://api.openalex.org/works?search=solid state battery&filter=from_publication_date:2025-01-01"

이것을 AI에게 시킬 때는 명령을 외울 필요가 없습니다. "법제처 API로 소부장특별법 조문 받아와 줘"라고 말하면 됩니다.

도구가 안 붙을 때 — 4단계 점검

  1. 주소가 살아 있는가 — 키 없이 호출해 오류 메시지라도 오는지 확인(오면 주소는 생존)
  2. User-Agent 문제인가 — 열린국회정보 등은 브라우저 UA가 없으면 차단됩니다
  3. 키 문제인가 서비스명 문제인가 — 오류코드를 읽으면 원인이 갈라집니다
  4. 그래도 안 되면 우회 — fetch로 공개 페이지를 읽거나, 파일로 내려받아 kordoc·filesystem으로 처리

무엇을 넣지 않을지부터 정합니다

⚠ 외부 AI 서비스에 넣지 않는 것
  • 미공개 과제·평가 자료 — 우수성과 평가 원시데이터, 심사 중 내부 검토자료
  • 연구자 개인정보가 포함된 원자료 — 이름·등록번호 등은 개인정보 제거 단계를 거친 뒤에
  • 비공개 회의 녹취 — 외부 전사 서비스(Tiro 포함) 이용 전 기관 규정 확인
  • 인증키·계정 정보 — 대화창에 붙여넣지 않습니다
  • 내부 시스템 전용 데이터 — 업무망 자료를 외부로 내보내지 않습니다
구분판단 기준
써도 되는 것이미 공표된 자료 · 공개 API로 누구나 받을 수 있는 데이터 · 내가 쓴 초안의 문장 다듬기
조건부공개 예정이나 아직 미공표 — 공개 시점 이후로 미루거나 기관 승인 절차를 따름
안 되는 것위 경고 상자 항목 전부
판단의 책임 도구가 아니라 사용자의 판단이 산출물의 책임을 집니다. AI가 만든 표·수치·인용은 전부 원자료와 대사한 뒤에 보고서에 실으십시오. 특히 위험한 것은 틀린 답이 아니라 그럴듯하게 틀린 답입니다 — 존재하지 않는 조문 번호, 미묘하게 어긋난 기준연도, 출처가 실재하지 않는 통계.

검증 3원칙

  1. 수치는 원자료와 대사한다 — API 원본과 보고서 표를 1:1로 맞춰 봅니다
  2. 인용은 실재를 확인한다 — 법령 조항·통계표·논문은 실제로 열어 확인합니다(korean-law-mcp의 인용 검증 활용)
  3. 확인 못 한 것은 확인 못 했다고 쓴다 — AI에게도 "확인 안 되면 '확인불가'로 두고 추정하지 마"라고 명시하십시오. 이 한 문장이 할루시네이션을 크게 줄입니다
